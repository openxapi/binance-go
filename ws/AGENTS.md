# Repository Guidelines

This repository hosts the autogenerated Go WebSocket clients for Binance products. Treat every package as generated code: prefer adjusting the upstream AsyncAPI specs or templates in `openxapi/openxapi` and then regenerating rather than hand-editing files here.

## Project Structure & Module Organization
- Root `go.mod` unifies all Binance product packages; each product lives under its own module directory (`spot`, `spot-streams`, `umfutures`, `cmfutures`, `options`, `pmargin`, `pmarginpro`, plus their `*-streams`).
- Every module mirrors the same layout: request/response types sit under `models/`, clients and connection logic live next to them. Keep new files co-located with the product they serve.
- Shared assets (like README snippets) stay at repo root; avoid cross-importing between products to keep each package publishable via `go get`.

## Build, Test, and Development Commands
- `go build ./spot` (replace `spot` with any package) to ensure the targeted client compiles.
- `go test ./spot/...` for unit tests; add `-run TestName` when iterating on a single scenario.
- `BINANCE_API_KEY=xxx BINANCE_SECRET_KEY=yyy go test -v ./spot-streams` runs authenticated integration tests; unset keys when finished.
- `go test ./...` at repo root before opening a PR to catch regressions across all products.

## Coding Style & Naming Conventions
- Format with `gofmt` (or `goimports`) before committing; CI assumes idiomatic Go formatting and tabs for indentation.
- Exported structs and methods use PascalCase mirroring Binance terminology (`MarkPriceEvent`), private helpers stay camelCase.
- Keep generated naming patterns intact (request builders `<Action>Request`, stream handlers `Handle<Event>`); deviations break regeneration diffs.

## Testing Guidelines
- Favor table-driven tests for serializers/deserializers and mock WebSocket interactions.
- When adding integration coverage, isolate credentials via env vars only and document any required symbols or listen keys inside the test.
- Name tests `Test<Product><Behavior>` (e.g., `TestSpotStreamsReconn`) to keep `go test` output navigable.

## Commit & Pull Request Guidelines
- Follow the concise imperative style seen in history (`Refactor spot-streams`, `Fix cmfutures auth`). Mention the affected package first when possible.
- Reference the AsyncAPI spec or template change that motivated the regeneration, and include reproduction steps if you ran `openxapi` locally.
- PRs need: summary of generated surface changes, test evidence (`go test ./pkg/...` output), and any docs/screenshots for new endpoints.

## Security & Configuration Tips
- Never commit API keys or listen keys; rely on environment variables and `.envrc` entries ignored by Git.
- When troubleshooting connectivity, point clients to testnet endpoints (`SetActiveServer("testnet1")`) before touching production keys.
